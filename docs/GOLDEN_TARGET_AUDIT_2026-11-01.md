## اختبارات منع التكرار

- `src/server/audit.test.ts`: سيناريوهات HTTP مع خوادم وقواعد مؤقتة: PIN، الجلسة وحد المحاولات، العملاء، فشل SQLite الفعلي عبر trigger، الدفعات والاستردادات، البنود، الهوية والربط، الروابط الرمزية، مراقبة الخلفية، التصدير، تراجع المعاملة، نموذج مالي قديم وعميل مؤرشف.
- `src/server/productionFiles.test.ts`: فرض كتابة منافسة في الوجهة، ثم فرض إنشاء مصدر جديد أثناء النقل؛ التحقق من بقاء المحتويين دون استبدال أو حذف المنافس.
- `src/server/productionIdentity.test.ts`: هوية ثابتة عند تغيير الاسم والحجم والطابعة، هوية جديدة لملف بديل، دقة bigint، تحليل الكمية والأبعاد وترميز التصدير.
- توسيع اختبارات السجل وأرقام واتساب الموجودة. أُدرجت الاختبارات الجديدة في `test:management` عبر `test:audit`، وبالتالي في CI الموجود.
- `scripts/verify-workspace.cjs`: يبدأ خادماً وChrome خاصين به بدل قراءة .env والاتصال بخادم ومتصفح قائمين. يغطي الصفحات الثماني، الهاتف 390px، العربية والإنجليزية، المظهر، البحث، فشل الحفظ والتحديث، انقضاء الجلسة والخروج، عرض الذمم وحقل البحث.

قبل الإصلاح فشلت الاختبارات الثمانية الأولى، وفشل اختبار سباق الوجهة. ثم أعيد إنتاج سباق حذف المصدر واختبار العميل المؤرشف باختبارات حمراء قبل إصلاحهما. لم تُضعف الاختبارات القديمة أو تُحذف.

كشف تشغيل gstack عبر Bun أيضاً أن أول رصد كان يتأخر دورة كاملة وأن مؤقت الخلفية لا يحترم فترات التحديث الأقصر. صار فحص الموعد كل ثانية، والرصد وفق الفترة المضبوطة؛ لم تُرفع مهلة الاختبار ولم يُلغَ أي تحقق.

تحسينات التصميم السريعة المنفذة: عنوان بحث دائم، تسمية أدق للإنجاز التاريخي، إبقاء الذمة ظاهرة أثناء إعادة العمل، والاحتفاظ بنموذج التفاصيل عند فشل الحفظ. حُفظ المظهر العام دون إعادة تصميم.

## قيود ومخاطر باقية قبل أي نشر

1. **P1: ترابط البيانات التاريخية.** المعرّفات الجديدة لا تُرحّل الروابط القديمة المعتمدة على الاسم تلقائياً، ولا تدمج أموالاً بناءً على تخمين. قد تظهر الملفات القديمة كملفات غير مربوطة بجانب تاريخها المحفوظ. يلزم تقييم ترحيل مستقل على نسخة احتياطية تجريبية واعتماده قبل تطبيقه على بيانات العملاء. لم تُنفذ أي عملية كهذه.
2. **P1: انقطاع الطاقة بين القواعد.** معاملة ATTACH تختبر rollback عند فشل SQL، لكنها لا تضمن commit ذرياً لملفات SQLite منفصلة تعمل بنمط WAL عند انقطاع الطاقة. يلزم قرار تخزين/تعافٍ مستقل قبل الاعتماد المحاسبي الحرج. [توثيق SQLite](https://www.sqlite.org/lang_attach.html).
3. **P2: توافق التخزين.** النقل الآمن يتطلب هوية ملفات موثوقة ودعم hardlinks. يرفض التخزين غير المدعوم بدل نسخ البيانات وفصل الهوية. اختُبر على تخزين Windows المؤقت فقط؛ لم تُختبر مشاركة الطباعة الحقيقية. إذا تعارض استرجاع staging، تبقى النسخة محفوظة ويظهر اسم مجلد الاستعادة للمراجعة اليدوية.
4. المسح الدوري ليس عداد الطابعة ولا يضمن التقاط ملف يُضاف ويُحذف بين مسحين. وقت done هو وقت الرصد، لا وقت الطباعة الفعلي. مجلدات التاريخ التي لا تتضمن سنة تبقى ملتبسة بين السنوات.
5. التصدير JSON ليس استعادة تم اختبارها ولا لقطة متزامنة مضمونة للقواعد الثلاث. يلزم اختبار النسخ والاستعادة بطريقة SQLite آمنة قبل النشر.
6. واتساب الرسمي لم يُختبر باتصال أو إرسال حقيقي؛ اختبارات تطبيع الأرقام وربط العملاء محلية. ولم تُختبر طابعات حقيقية أو صلاحيات الشبكة.
